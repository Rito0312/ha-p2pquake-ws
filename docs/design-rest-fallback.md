# 設計: REST（JSON API）による予備受信

2026-11-07 作成。設計レビュー（別エージェント）の指摘を反映済み（末尾「レビューでの変更」）。

## 背景
- 11/06 19:39 関東東方沖（最大震度3）と 11/07 20:07 茨城県沖（最大震度3）で、WebSocket の 551 受信が P2P の登録時刻（`time`）から 2〜6 分遅れた。小さな地震では 0.6〜1.1 秒
- 同時間帯、HA の他の処理や同じ api.p2pquake.net への REST 取得（HA 標準 REST センサー、556、60 秒間隔）は正常。遅れた受信の直後に WebSocket が close_code=1006 で切断
- 原因は P2P の WebSocket 配信側の混雑と推定（断定はできない）。どこが原因でも、受信経路を増やせば影響を抑えられる
- 現状、556 は HA 標準 REST センサー（configuration.yaml、10 秒間隔）でも受けているが、この経路では画像が作られない。551 には予備がない

## 目的
- WebSocket が遅れた・切れたときも、556 と 551 を JSON API から取得し、WebSocket と同じイベント（`p2pquake_eew` / `p2pquake_quake`）と画像を作る
- 先に届いた方だけを処理する（重複を発火しない）
- 将来、HA 標準 REST センサーと地震検知オートメーションの REST・起動時トリガーを外せるようにする（外すのは、この機能の本番での動作確認の後。今回の範囲外）

## 確認済みの事実
- WebSocket の `_id` と JSON API の `id` は同じ値（11/07 20:50〜20:51、555・561 の 3 件で一致を確認）。既存の `message_id()` は両方を見るので、同じ重複除去で WS と REST をまたいで除ける
- 応答サイズ（gzip、aiohttp は既定で gzip を要求）: `codes=556&limit=1` は速報がなければ `[]`（2 バイト）。`codes=551&limit=3` は約 7KB（直近が観測点 558 件の地震のとき。非圧縮 44KB）
- 公式のレート制限: `/v2/history` は 60 リクエスト/分/IP。HA 標準 REST センサーが 6 回/分を使っている

## 構成
- 新規 `poller.py`（HA 非依存、`client.py` と同じ方針）: `P2PQuakePoller`
  - `run()` で 556 と 551 を別々の周期で取得し続ける。`stop()` で止まる
  - 取得した各要素を、`P2PQuakeClient` と共有する受け口に渡す（下記）
- `client.py`: `handle_raw` の重複除去と callback 呼び出しを `handle_data(data, source)` に切り出し、WS は `source="ws"`、REST は `source="rest"` で呼ぶ。Deduplicator は 1 つを共有（WS と REST のどちらが先でも、後から来た方は捨てる）
  - callback の型を `(data, source)` に変更
- `__init__.py`: `_on_message(data, source)` に変更し、イベントに `_source`（"ws" / "rest"）と `_p2p_delay`（受信時刻 − P2P の `time`、秒。読めなければ付けない）を追加。画像・保留・`_area_scales` などの処理は既存のまま（どちらの経路でも同じ処理を通る）
  - サンドボックス接続のときは REST を動かさない（サンドボックスに JSON API の過去データは無い）

## 取得の周期
| 対象 | URL | 通常 | 地震の直後・WS 未接続のとき |
|---|---|---|---|
| 556 | `/v2/history?codes=556&limit=3` | 10 秒 | 10 秒 |
| 551 | `/v2/history?codes=551&limit=3` | 60 秒 | 15 秒 |

- 「地震の直後」= WS か REST で新しい 551 か 556 を受け取ってから 15 分間
- 「WS 未接続」= `client.connected` が False の間
- 1 分あたり: 556 が 6 回 + 551 が 1〜4 回 = 最大 10 回。HA 標準 REST センサーと合わせて最大 16 回（上限 60）
- データ量: 551 が通常 1 回/分 × 約 7KB = 約 10MB/日
- 失敗時（タイムアウト・接続エラー・HTTP 429/5xx・JSON でない）: その周期は飛ばし、連続失敗ごとに待ちを 2 倍（最大 60 秒）。成功したら元の周期に戻す。ログは連続失敗の 1 回目だけ WARNING、以降 DEBUG（client と同じ方針）
- 1 回の取得のタイムアウトは 8 秒

## 古い情報の扱い
- 応答は新しい順なので、古い順に処理する（restart モードのオートメーションで最新が最後に残るように）
- 起動後の最初の成功した取得: 全要素を「処理済み」として登録だけする（発火しない）。ただし 556 で `time` が 180 秒以内のものは発火に回す（既存の起動中保留の仕組みにのる。HA 起動時トリガーの代わり）
- 2 回目以降: `time` が古すぎるものは発火せず「処理済み」として登録だけ（556 は 600 秒、551 は 1800 秒より前）。障害から戻ったときに古い情報を流さない
- `time` が読めない要素は発火しない（登録のみ。DEBUG ログ）
- `time` は日本時間（`YYYY/MM/DD HH:MM:SS.fff`）として解釈する

## エンティティ
- 追加: `binary_sensor`「REST 取得」（device_class: connectivity。直近の 556 の取得が成功していれば on。連続失敗が 60 秒を超えたら off）。属性に最後に成功した時刻
- 監視オートメーションは後で、HA 標準 REST センサーのチェックをこれに置き換える（今回の範囲外）

## 既知の制約
- 起動時の最初の取得で 551 を「処理済み」登録するため、起動直後に WS から遅れて届いた同じ 551 は表示されない（起動直後だけ）
- P2P のサーバー自体が止まれば WS も REST も止まる（別の配信元は今回の範囲外）
- 重複除去は直近 1000 件。REST は 1 回最大 3 件 × 2 種類なので十分

## テスト
- poller: 周期の切り替え（通常 / 地震の直後 / WS 未接続）、初回の登録のみ・180 秒以内の 556 の発火、古い要素の破棄、時刻の読めない要素、失敗時の待ちの伸び方と復帰、ログの出し方、古い順の処理
- client: WS と REST をまたぐ重複除去（どちらが先でも 1 回だけ）
- 統合: `_source`・`_p2p_delay` の付与、REST 経路でも画像が作られること、サンドボックスでは REST が動かないこと、unload で止まること

## レビューでの変更（2026-11-07）
上の本文より、この節を優先する。

### 重複除去
- WS と REST の重複除去と配送は、独立した `Ingest`（`ingest.py`）にまとめる。`client.py` は 551・556 だけを `Ingest` に渡す（555・561・9611 などは重複除去の枠に入れない。強い地震で 561 が大量に届いても 551・556 の記録が押し出されない）
- 記録は**発火の直前**に行う（後の処理で例外が出ても、同じ要素を何度も発火しない。「多くても1回」を優先）。記録の確認から登録までの間に await を入れない
- id の無い要素は、REST では捨てる（WS は従来どおり通す）
- 重複除去の記録は `hass.data[DOMAIN]` に置き、オプション変更による再読み込みをまたいで残す
- 556 は eventId ごとに最大の serial を覚え、古い報が後から届いたら発火はするが画像と `last_eew` は更新しない（オートメーション側は eventId で1回だけ動くので影響なし）

### 初回の扱い（「最初の成功」ではなく時刻で決める）
- 統合の setup 時刻より前の `time` を持つ要素は登録だけ。ただし HA の起動中（CoreState が running でない）に限り、556 で `time` が 180 秒以内のものは発火に回す（既存の起動中保留にのる）
- setup 時刻以降の要素は通常の年齢判定（556 は 600 秒、551 は 1800 秒より古ければ登録だけ）
- 551 の取得は `async_at_started` の後に始める（起動中の 551 は従来どおり発火しないため）

### 取得とバックオフ
- 556 は limit=10（速報が無ければ 2 バイト）、551 は limit=3
- 開始時刻を基準にした固定周期。前の取得と重ねない。556 と 551 は別々のループ・別々のバックオフ
- 待ちを伸ばすのは HTTP 429・5xx のときだけ（2 倍、最大 60 秒）。429 は Retry-After に従う。タイムアウト・接続エラーでは周期を保つ
- 「WS 未接続」での周期切り替えは削る。551 は「新しい 551・556 を受け取ってから 15 分は 15 秒、それ以外は 60 秒」だけ
- 応答は `json(content_type=None)` で読み、1MB を超えたら失敗。list でない応答・dict でない要素・code の不一致は失敗として数える
- `time` は固定の +09:00 で解釈（zoneinfo は使わない）。ミリ秒なしの形式も受ける

### REST 取得の状態センサー
- `binary_sensor`（connectivity）: is_on = 「556 の直近の成功から 60 秒以内」。30 秒ごとのタイマーで再評価する（取得ループが止まっても off になる）
- 取得タスクが予期せず終わったら ERROR を出して off（WS と同じ扱い）
- 状態が変わったときだけ書き込む（「最後に成功した時刻」は属性にしない。recorder に 10 秒ごとに書かない）。専用のシグナルを使う
- サンドボックス接続では作らない

### イベントの形
- `_message_id` を正とし、REST の要素にも `_id` を補う（WS と同じ形にする）
- 実際の API 応答と WS データを fixture にし、描画・`area_scales`・センサーが同じ結果になることを試験する

### 追加するテスト
- 561 を 1500 件流した後に、同じ 556 を REST で受けても発火しない
- 発火後の処理で例外が出ても、REST の次の取得で再発火しない
- id の無い REST 要素は捨てる
- 起動時の回線不調で最初の成功が遅れても、setup 後の 551 は発火する
- 取得タスクが止まったら状態センサーが off になる
- 再読み込みで 180 秒以内の 556 が二重に発火しない
- 429 の Retry-After、タイムアウトでは周期を保つこと
